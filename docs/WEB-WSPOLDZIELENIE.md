# Shared organization vaults (web variant): contract

Status: implemented (server: `crates/node/src/vaults.rs`, `websync.rs`; client: `ui/src/vaults.ts`, `browserauth.ts`, `signing.ts`, `notifications.ts`, `records.ts` conflicts). Stage E (box keys, rotation, removal race) is implemented too; protected projects are in progress. This file is the contract between the server (`crates/node`) and the browser client (`ui/src`). Change it only together with both sides.

## Model

- A **vault** has an id (`v-` + 32 lowercase hex), a name, a kind (`notatki` | `organizacja`) and an owner (`ownerUserId`).
- The legacy personal vault `browser-<userId>` keeps working unchanged: it is implicitly owned by that user, has no members table rows, and is never shareable.
- **Personal vault key (docs/MCP.md §3.7).** The personal vault gets a random key of its own, so that a chat can later be given it without the personal key. Epoch 1 is the personal key itself (never stored). `GET /api/me/personal-key` → `{ keys: [{ keyEpoch, wrappedKey }] }` (oldest first; `wrappedKey`: `notes-key-v1` under the personal key, AES-GCM with AAD `notes-personal-vault-key-v1\0<userId>\0<keyEpoch>`, so another wrapped key of the user, such as a shared vault's, never unwraps as one). `PUT /api/me/personal-key` `{ keyEpoch, wrappedKey }` takes only the next epoch (current + 1, from 2) and never replaces a stored one: the same key again is a no-op, another one is `409` ("Ten klucz Moich notatek został już zmieniony na innym urządzeniu."), and the owner's open sockets get `rekey`. Rows carry `createdAt`; a chat with the personal vault in its cert revoked after the newest key was made (any way: the person, another device, `revoke-all`) makes the next open of Moje notatki rotate their key without it. Table `personal_vault_keys(user_id, key_epoch, wrapped_key, created_at)`, deleted with the account. Once epoch 2 exists, a put to `browser-<userId>` whose envelope `keyEpoch` is missing or lower than the current one gets `stale-key`; envelopes and relays then carry `keyEpoch`. The first client that opens the vault online migrates it: PUT epoch 2 (on `409` it takes the stored key), then sends the vault again under it and re-seals the file envelopes. The current and older keys are kept on the device in `epochKeys` (wrapped with the personal key) for offline reading. A recovery code is checked by unwrapping the stored key when the vault is under epoch 2 or later, or when the server holds a key but no snapshot yet; offline, by this device's copy of that key; with neither at hand every code is refused (a wrong code stored would lock the device out). A key of its own is made only once the personal key has opened the vault's data on this device (its local copy or the server's snapshot), or there is no data yet; with nothing to check a recovery code against and the server out of reach, every code is refused. The client takes a snapshot's `revision` only once that snapshot is decrypted and merged, and sends the vault again under a new key only after the server's state is merged, so a put of a device's own state can never pass as based on a newer state it has not read. The server learns that the personal vault has a key of its own and its epoch; it never sees the key.
- **Roles**: `owner` > `admin` > `editor` > `viewer`.
  - `viewer`: read (WS hello + snapshot + updates). Puts are rejected.
  - `editor`: viewer + put.
  - `admin`: editor + create/revoke invites, change roles of editors/viewers, remove editors/viewers.
  - `owner`: everything; can change any role, including promoting someone to owner. A vault must always keep at least one owner. Exactly one `ownerUserId` is recorded at creation (used in the AAD); it never changes.
- **Vault key**: a random AES-GCM-256 key generated by the creating client. The server never sees it.
  - Each member stores their own copy as `wrappedKey`: the raw vault key encrypted with that member's personal account key (the AES key from their recovery code), as an `Envelope` (`schema: "notes-key-v1"`, nonce 12 B base64, ciphertext base64). The server stores it opaquely; it validates only shape (base64, nonce 12 B, ciphertext ≤ 4 KiB).
  - **Invites carry the key in the URL fragment**: `https://host/?invite=<token>#k=<base64url raw vault key>`. The server never receives the fragment. The invite token expires (default 7 days) and admits up to `maxUses` different people (1–50, default 1); each person joins once. Trade-off, documented on purpose: a multi-use link carries the vault key, so anyone who holds it can join until it is used up or revoked. Admins can revoke unused invites; the link is "used up" when its uses reach `maxUses`.
  - Removing a member revokes server access immediately (REST + WS). It does not rotate the key (shortcut: key rotation is a later stage).
- Vault snapshot encryption is unchanged (`notes-encrypted-v1`, AES-GCM), with AAD = `notes-encrypted-v1\0<ownerUserId>\0<vaultId>`. The snapshot's `vault.ownerUserId` is the vault owner, not the current user.

## REST (all JSON, session cookie, mutations require same-origin like `/api/auth/*`)

| Method & path | Who | Body → Reply |
|---|---|---|
| `GET /api/vaults` | any user | → `{ vaults: [{ id, name, kind, ownerUserId, role }] }` (shared vaults only; the client adds `browser-<me>` itself) |
| `POST /api/vaults` | a user with `personal = "allowed"` | `{ name, kind, wrappedKey }` → `201 { vault: { id, name, kind, ownerUserId, role: "owner" } }`. An account made from an invite link alone (`personal` `off`/`requested`) → 403 until the server admin agrees (docs/PANEL-ADMINA.md) |
| `GET /api/vaults/:id` | member | → `{ vault, role, wrappedKey, members: [{ userId, email, name, role, addedAt, signingKey, boxKey, profile }] }` (no last name: see "Encrypted last name") |
| `PUT /api/vaults/:id/my-profile` | member (viewer too) | `{ profile: <notes-profile-v1> \| null }` → `204`; 404 for non-members |
| `PATCH /api/vaults/:id` | admin+ | `{ name }` → `{ vault }` |
| `DELETE /api/vaults/:id` | owner | `{ name }` (the vault's exact name, typed by the owner to confirm) → `204`. 400 when the name differs, 403 for admins and below, 404 for non-members and personal vaults. Deletes the vault for everyone: the row, members, invites, assignments and leases (cascade), the chats' rows for the vault (`agent_keys`, `agent_scopes`, `agent_proposals`, `agent_detached`, `vault_agent_policy`), the shared snapshot in `browser-sync.db`, file scopes and the quota. File rows become expired trash, so the next reconciliation pass removes them and their objects. Every former member's open sockets get `access` with `role: null`, as on a removal. Copies already in members' browsers stay there, encrypted. The deletion writes the id to `deleted_vaults` in the same transaction, and the entry stays for good. Every start drops the snapshots and files of all listed vaults again (`finish_deletion`, `run.rs` `open_services`, idempotent), so a deletion cut short, or a `browser-sync.db`/`files.db` restored from an older backup, is finished then. Only listed ids are touched: a vault table restored from an older backup never makes live vaults look deleted. `notes-node files-check` opens the same services, so it finishes deletions too. |
| `POST /api/vaults/:id/invites` | admin+ | `{ role: "admin"\|"editor"\|"viewer", maxUses?: 1..50 (default 1) }` → `201 { invite: { id, token, role, expiresAt, maxUses } }` (token: 32 random bytes hex; only its BLAKE3 hash is stored). Any other `maxUses` → 400 "Liczba osób musi być od 1 do 50." |
| `GET /api/vaults/:id/invites` | admin+ | → `{ invites: [{ id, role, createdBy, createdAt, expiresAt, maxUses, uses }] }` (unused, unexpired only, i.e. uses < maxUses; never the token; remaining = maxUses − uses) |
| `DELETE /api/vaults/:id/invites/:inviteId` | admin+ | → `204` |
| `GET /api/invites/:token` | any user | → `{ vault: { id, name, kind, ownerUserId }, role, expiresAt, maxUses, uses }` or 404/410 |
| `POST /api/invites/accept` | any user | `{ token, wrappedKey, keyEpoch }` → `{ vault: {..., role} }`. Each accept adds one use (`uses+1`), and the link is spent when `uses` reaches `maxUses` (410 from then on, like an expired one). 410 if spent/expired, 409 if already a member |
| `PATCH /api/vaults/:id/members/:userId` | admin+ (rules above) | `{ role }` → `{ member }`; 409 when it would leave no owner |
| `DELETE /api/vaults/:id/members/:userId` | admin+ (rules above), or the member themselves (leave) | → `204`; 409 when it would leave no owner |

Errors: `{ message }` in Polish, like the existing auth errors. 401 when not logged in, 403 when the role is too low, 404 when the vault doesn't exist **or** the user isn't a member (don't leak existence).

## WebSocket `/api/sync/ws` (existing frames, extended)

- `hello { vaultId, revision?, nonce? }`: allowed when `vaultId == browser-<me>` (legacy) or the user is a member. Otherwise the server sends `{ type: "error", code: "forbidden", message }` and closes.
- Snapshot storage for shared vaults is per vault (not per user): all members see one revision sequence. The legacy personal vault keeps its per-user row.
- Rooms are keyed by vault id for shared vaults, so a put by one member is published as `update` to every other member's socket.
- `put` from a `viewer` → `{ type: "error", code: "read-only", message }` (socket stays open).
- When a member is removed or downgraded, the server sends `{ type: "access", role: "<new role>" | null }` to that user's open sockets for the vault; on `null` it closes them.
- `ack`, `snapshot`, `update`, `conflict` unchanged.
- `relay { envelope }`: a live edit. The server checks the sender's role (editor and up; viewer → `read-only` error; non-member → `forbidden` and close) and passes the frame unchanged to the vault's other sockets as `{ type: "relay", envelope }`. It is never stored. The envelope is AES-GCM with the vault key and AAD `notes-relay-v1\0<ownerUserId>\0<vaultId>`, over JSON `{ schema: "notes-relay-v1", notes: [{ id, update }] }` (`update`: a Yjs update, base64). Notes of protected projects are never relayed. The snapshot put stays the record: a lost relay is healed by the next put (sent 2 s after typing pauses, at least every 10 s, and when the page is left).

### Połączenie (keepalive, reconnect, coalesced updates; 2026-11-17)

- `ping` → `{ type: "pong" }`. The client pings every 25 s (never two at once); a ping with no frame back within 15 s
  means a dead link, and the socket is given up and a new one opened (the old one's late `close` is ignored). Judged by
  the ping's answer, not by wall time: a hidden tab's timers run about once a minute. A tab that becomes visible again
  pings at once and checks the answer 16 s later. The server sends a WebSocket protocol ping every 30 s (browsers answer
  it themselves, so tabs still on an older client stay open too) and closes a socket that sent nothing for 90 s.
  Cloudflare closes idle WebSockets after 100 s, and a dead link (sleep, a Wi-Fi change) never reports itself, so
  without this a member looked "synced" while nothing arrived. Client pings are limited to 1/s (burst 5); extra ones
  get no answer.
- Reconnects wait `1 s · 2^(n-1)` (at most 30 s) plus up to 1 s of jitter, so members don't all come back at the same
  moment after a server restart; the count resets with the next `snapshot`. `online` and a tab becoming visible again
  reconnect at once.
- `hello.revision` + `hello.nonce`: a reconnecting client names the revision it holds and the nonce of that revision's
  envelope, but only when every put it sent got its answer (ack, conflict, or a read-only/stale-key/slow-down error;
  answers come in order), nothing is unsent, and its saved state is that revision's. When the server's revision and
  that envelope's nonce are both still the same (a restored database can repeat a revision number) it answers
  `{ type: "snapshot", revision, envelope: null, unchanged: true }` instead of the whole vault. A first open never sends
  `revision`, and `envelope: null` without `unchanged` still means "the server has no vault yet".
- Each socket gets at most one full `update` per 2 s. Puts landing meanwhile reach it as one `update`, the newest one,
  when the interval ends (each revision contains every earlier one; text edits already arrive at once as `relay`). A
  chat's revision (`author.agentId`) is never folded: the held-back update goes first and the chat's at once, since the
  client checks a chat's changes against the revision just before it (docs/MCP.md §7.1). A revision the socket already
  has (its own ack, a `conflict`, a `snapshot`) is never sent again as `update`.
  With several members typing, every member used to download the whole vault after each put of each other member.

## Snapshot format additions (client only, schemaVersion stays 1, fields optional for old data)

- The plaintext inside the AES-GCM envelope is the snapshot JSON gzipped (it starts with `1f 8b`). A plaintext that starts with `{` is an older, uncompressed copy and is still read. The server never sees the difference.
- Clients compare their state with the server's without the reader's own fields (`state.me`, `state.organization.me`), so merging an update never sends the vault straight back.

- `state.deleted: [{ id, path, deletedAt }]` tombstones; a tombstoned id is never resurrected by merge (see `bridge.ts`).
- `state.notes[].pathChangedAt`: ms timestamp of the last rename; merge picks the later path (last writer wins), and resolves path collisions by renaming to `name (konflikt N).md` instead of throwing.
- Later stages (D): `state.organization.events` entries carry `signature` + `signerUserId`; member public signing keys come from `GET /api/vaults/:id` (`members[].signingKey`, JWK, ECDSA P-256).

## Stage D: signing keys, signed history, notifications (contract)

Server (`crates/node`):

| Method & path | Who | Body → Reply |
|---|---|---|
| `GET /api/me/signing-key` | any user | → `{ publicJwk, wrappedPrivate }` or 404 when not set |
| `PUT /api/me/signing-key` | any user | `{ publicJwk, wrappedPrivate }` → `200 { publicJwk }`; 409 when a different key is already set (rotation is a later stage) |
| `GET /api/vaults/:id` | member | `members[]` gains `signingKey: publicJwk \| null` |

- `publicJwk`: ECDSA P-256 public JWK (`kty: "EC"`, `crv: "P-256"`, `x`, `y`, nothing private like `d`), JSON ≤ 1 KiB.
- `wrappedPrivate`: `notes-key-v1` envelope (as `wrappedKey`): the PKCS#8 private key encrypted with the user's personal key. ciphertext ≤ 4 KiB.

Client:
- Every organization event (`TaskEvent`, record operation) created by this user gets `signerUserId` and `signature` (base64 ECDSA P-256/SHA-256 over the canonical JSON of the event without `signature`).
- On display, an event whose signature doesn't verify against the signer's key from `GET /api/vaults/:id`, or whose signer isn't a member, is marked "niezweryfikowane". It is never silently dropped.
- Notifications are derived locally from signed events that concern the current user (assigned, unassigned, supervisor set, due date changed, task done), minus those the user already read. The read state is per user and lives only in that user's local storage.
- Calendars and inventories: concurrent edits of the same event/item from two members are detected at merge (same target, neither operation saw the other) and shown as a conflict with both versions and a choice. They are never silently overwritten.

## Stage E: key rotation, protected projects, removal race (contract)

### Box keys (public-key encryption to a member)
- Every user also has an ECDH P-256 **box key**: `GET/PUT /api/me/box-key` with exactly the same shapes and rules as `/api/me/signing-key` (`{ publicJwk, wrappedPrivate }`, 404 when unset, 409 for a different key). `GET /api/vaults/:id` → `members[].boxKey: publicJwk | null`.
- **Sealed box** `notes-sealed-v1` (JSON): `{ schema: "notes-sealed-v1", epk: <ephemeral ECDH P-256 public JWK kty/crv/x/y>, nonce: <12 B base64>, ciphertext: <base64> }`. Key = HKDF-SHA256(ECDH(ephemeral, recipient), salt = 32 zero bytes, info = "notes-sealed-v1") → AES-GCM-256. Server validates shape only (epk like publicJwk, nonce 12 B, ciphertext ≤ 4 KiB).

### Vault key epochs and rotation
- A vault has `keyEpoch` (integer, starts at 1). `GET /api/vaults` and `GET /api/vaults/:id` return `vault.keyEpoch`. `GET /api/vaults/:id` returns `wrappedKeyEpoch` (epoch of this member's `wrappedKey`), `pendingKey: { keyEpoch, sealedKey } | null` and `needsRotation: boolean`.
- Snapshot `Envelope` gains optional `keyEpoch` (integer). For shared vaults the server rejects a put whose `keyEpoch` is missing or lower than the vault's with `{ type: "error", code: "stale-key", message }` (socket stays open).
- `POST /api/vaults/:id/rotate` (admin+): `{ keyEpoch: <current+1>, keys: [{ userId, sealedKey }] }`. It must list exactly the current members (else 409). The server stores each as that member's `pendingKey`, sets `keyEpoch`, clears `needsRotation`, revokes all unused invites (their links carry the old key), and publishes `{ type: "rekey", keyEpoch }` to the vault's sockets. Reply `{ vault }`.
- `PUT /api/vaults/:id/my-key` (member): `{ keyEpoch, wrappedKey }`, with `keyEpoch` equal to the vault's current one. It replaces this member's wrappedKey and epoch and clears their pendingKey.
- **Removing a member or a member leaving** sets `needsRotation = true`. Any admin+ client that sees `needsRotation` (on open, after a removal it made itself, or on an `access`/`rekey` event) rotates: new random vault key, a sealed box per remaining member (to their boxKey; a member without a boxKey can't be rotated to, and the rotation is refused client-side with a Polish message listing them), POST rotate, re-encrypt and put the snapshot with the new epoch.
- **Members** on `rekey`, or on a decrypt failure / `stale-key`: GET the vault, unseal `pendingKey` with their box private key, PUT my-key, and keep the old epoch keys locally to read their local copy. They then merge the server snapshot and continue.
- **Invites** carry the current key and its epoch (`#k=<key>&e=<epoch>`). `POST /api/invites/accept` requires `keyEpoch`; a mismatch with the vault's current epoch → 410 "Zaproszenie wygasło po zmianie klucza." Rotation deletes unused invites, so an old link then gets 404.

### Removal race
- A put must not commit after the remover's DELETE has returned. Role check and commit of a put, and member removal or role change, are serialized per vault (one lock shared by vaults.rs and websync.rs in the same process, or one database transaction).

### Protected projects (client only, inside the snapshot)
- A project is a folder `Projekty/<name>/` (existing). A protected project has its own random AES-GCM-256 project key, a member list (user ids, a subset of the vault members) and an epoch.
- Snapshot `state.protected: [{ path, keyEpoch, members: [userId], keys: [{ userId, sealedKey }], envelope, lead?, signerUserId, signature }]`. `envelope` is the AES-GCM (project key, AAD `notes-protected-v1\0<vaultId>\0<path>\0<keyEpoch>`) of JSON `{ notes, versions, deleted }` for the notes under `path` (same shapes as `state`). Notes under a protected path never appear in plain `state.notes`. `signature` (ECDSA, signer's signing key) covers the canonical JSON of the entry without `signature`.
- Merge: a member of the project decrypts and merges its notes normally (CRDT). A non-member keeps the incoming entry opaque: the one with the higher `keyEpoch`, or on a tie the server's. Non-members' clients never drop it.
- **Any folder or a single note** can be protected, not only `Projekty/<name>/`. A project note `Projekty/X/X.md` protects its folder; any other note protects itself (`path` is the note path). Entries of a note are checked with the same rules as a folder: a note is inside an entry when its path equals the entry's path or lies under it (`inside`). A protected note is not listed to non-members at all; a protected folder is listed only to the members who hold its key (no lock icon, no badge).
- Owner/admin manage any protected folder. The project lead manages the project folder and the folders inside it. The lead is the entry's `lead: { schema: "notes-project-lead-v1", vaultId, path, userId, signerUserId, signature }`, an appointment signed by an owner or admin of the vault for that vault and path (so any device checks it, whoever signed the entry last). `project_protect` and `project_set_members` take an optional `lead` (user id, `null` clears it); only an owner or admin may set or change it, otherwise "Prowadzącego zmienia właściciel lub administrator.". `project_protection` answers `lead` (the verified appointment's user id, else `null`). The project note's `prowadzacy:` (and `osoby:`, `grupy:`) is text anyone with edit rights can change: it gives no rights. A manager's device shows "Zmiana osób projektu w notatce: zatwierdź" when the note adds people or (for an owner or admin) names another lead than the entry, and only that approval writes them into the entry (docs/MCP.md §6). An editor of a protected folder may protect a folder inside it that has no protection yet (its first members: the editor and the owners/admins); after that only owner, admin or the lead change it. Notes have no protection of their own: `project_protection`, `project_protect` and `project_set_members` on a note act on its folder (the innermost protected one above it, else its own) and answer with that folder's `path`; `project_protect` on a `.md` path is refused. Entries made for a single note by older versions still work, and owner or admin can lift them. They can change members (seal the project key for each), and must rotate the project key when removing someone.
- **Editors**: an entry may name `editors: [userId]` (signed with the rest of the entry). A new protection starts with no editors ticked, so only the owners, admins and the one who protects may write; an entry with missing or empty `editors` (made before this rule) still means every member may edit. Otherwise the editors are the named members plus every owner, admin and the one who saved the entry. The entry's `members` and `editors` are intersected, so an editor is always a member. A member who is not an editor reads the notes but cannot write them: `apply_update` is dropped with a message, other writes are refused ("Masz tylko podgląd tej notatki lub folderu.").
  - Changing only the editors is a change of the entry under the same key (no rotation). Removing members still rotates.
  - Writers are checked on merge: the signer must be an owner or admin, an editor (or a member, when there are no editors). A change of `members` or `editors` against the stored entry of the same or an older epoch must be signed by an owner, admin or the project lead (the lead of the entry verified before); otherwise the entry is kept but flagged `unverified` ("Zmiana członków lub edytorów przez osobę bez uprawnień."). A `lead` with a bad signature or the wrong schema, vault or path, or one that differs from the baseline's while the entry's signer is not an owner or admin, flags the entry too ("Prowadzącego zmienia właściciel lub administrator."); an unverified entry's lead manages nothing. An appointment whose signer is no longer an owner or admin (or no longer in the vault) has lapsed: the project has no lead until one is appointed again, and the entry stays valid. **Baseline:** each device keeps the last entry it verified per path (members, editors, lead, epoch) in its local key store, wrapped with the personal key, and checks every later entry against it, also after a reload; a flagged entry never becomes the baseline. A device that never saw the project trusts the first entry it sees (its limit, as before).
  - **Honest limit**: the server cannot enforce editors. A modified client can still write to a note it is not an editor of. Other members' clients show that change as "niezweryfikowane", because the entry was signed by a non-editor. A replayed older appointment (an earlier lead of the same project) is caught by devices that hold the newer entry; a device that never saw the project before cannot tell.
- **Owners and admins are always members.** Sealing a project adds every owner and admin with a box key, and any owner who holds the project key adds a missing owner or admin with the same key on merge (no rotation). Owners and admins are always editors.
- Projects are private by default: a new project is protected at creation (its creator, an owner or admin, is appointed its lead; members = the lead, owners and admins), and any device that may manage a project (owner, admin, lead) protects every still-open project it sees, with its assigned people and groups (`osoby:`/`grupy:`), owners and admins. That first lock narrows who sees the project and appoints no lead: the note's lead waits for an owner's or admin's approval.
- An entry carries `noteIds` (the random ids of its notes, signed with the entry). The payload also holds the organization task events of those notes (`events`); every device drops events whose `note_id` is in some entry's `noteIds` (and task-copy rows whose path is inside an entry) from the plain state, so a protected task's title, people and dates never travel in the clear. A non-member's device forgets the history it got while the project was still open.
- **Deleting a folder** that holds a protected project (`delete_folder`, owner or admin only; others get "Chroniony projekt usuwa właściciel lub administrator."): the entry leaves as a mark `{ path, keyEpoch, unprotectedAt, deleted: true, noteIds }` in `state.unprotected`. Every device drops the entry and forgets those notes; the tombstones in the same snapshot delete them, with their path cut to the folder. A rename over a protected project is still refused.
- **Marks are signed** (`signerUserId`, `signature`, ECDSA over the canonical JSON without `signature`, like entries): a mark in `state.unprotected` (lifting a protection, or a deleted project) is applied only when an owner or admin signed it, or, for a note protected on its own by an older version, a member of the verified folder entry that takes it in. Any other mark, unsigned ones included, is ignored and not passed on.
- **A flagged entry** (`unverified`) takes no writes on any device ("Masz tylko podgląd…"), its payload is never sealed again under its key (whoever forged it may know that key), and an owner's or admin's device never signs it again (healing missing admins skips it). An owner or admin setting its members again always makes a new key.
- **Limit (trust on first use):** a device that never saw a project (a new device, a new member) has no baseline and trusts the first entry it gets: an entry a project member signed with changed members, or with an older owner's appointment of a lead revoked since, passes there. Devices that saw the newer entry flag it. Closing this would need a signed history or counter per project (later).
- **Known limits** (to be closed by a signed membership record per project, a separate task):
  - Member and lead changes are judged against the entry's last signer, but every writer re-signs the entry on save, so a change can be judged against the wrong person (a stale device can carry an older members list forward).
  - Any project member can flag a project, or lock other devices out of it, by signing an entry with a higher `keyEpoch` (for example one listing only themselves, with no keys for the others).
  - A new protection is trusted on first sight from any vault editor: a device without a baseline for that path accepts it, and devices that cannot open it hide that folder.
  - A lead appointment is not bound to a `keyEpoch`: after a project is unprotected, its former lead can protect it again with the old appointment.
  - Merge rule (1) can be bypassed by replaying an older entry of the same `keyEpoch` (signed before a note joined the project) together with a forged plain copy of that note: an incoming entry of the same epoch replaces the held one. Needs a signed per-project counter or history.
  - Merge rule (3) is not applied on a device that has no copy of the note (a fresh device admits a payload copy whatever the signer's vault role), nor to plain trash items and tombstones.
- UI: a non-member does not see a protected folder or note at all (no row, no name in the tree, lists, search or quick open; `list_tree` omits it). Members, owners and admins see the folder as any other folder, with no lock. A non-member's plain state never lists the folder's path (`folders`, `folderChanges` are dropped with the notes). The project view has "Chroń projekt" / "Członkowie projektu".
- Folders inside a protected folder are part of its payload (`folderChanges` of the sealed `notes-protected-v1` envelope): a folder created, renamed or deleted by a key holder is saved there, never in the plain state. A folder inside a project can be renamed by its members. **Moving** (`rename`, `rename_folder`, the explorer's drag and drop) a note or folder into, out of or between protected folders is allowed: the item takes the protection of the folder it lands in (none, in a plain folder). The mover needs the key and the edit right at both the source and the target ("Projekt jest chroniony. Nie masz do niego klucza.", "Masz tylko podgląd tej notatki lub folderu."); the top-level rule below still applies. On the next save each touched entry is resealed and re-signed with its new `noteIds`, and the moved notes (with their versions and task events) go in the target's payload or the plain state. A device that cannot open the target forgets the moved notes by the target entry's `noteIds` (also when it holds a folder nested in the target); it does so for a note in a folder it holds only when that folder's own signed `noteIds` no longer list it. Deleting a project right after moving a note out of it does not delete that note: the deleted mark's `noteIds` leave out the notes held here outside the folder. Merge rules that keep this safe: (1) before the held payloads merge, every plain copy of a note that some entry lists is dropped from the incoming state, so a forged plain copy (an id read from the public `noteIds`, with a later `pathChangedAt`) cannot pull a protected note out; (2) a payload's notes, tombstones, trash and folders count only inside its path and outside the folders nested under it, and never for a note held here in another held project whose own `noteIds` still list it, nor (with no copy here) for a note another held entry lists too: then neither entry places it. What a device holds back from a payload stays with that entry and is sealed again with it, so a reseal never drops a note the device could not place; (3) an entry's `noteIds` take a note held at a plain place (forget it, keep it out of the plain export, or admit its payload copy) only when the entry's signer is a vault owner, admin or editor and the entry is not flagged, so a project member who only views the vault cannot hide a plain note from the others. **Limits:** a note that two held entries list stays out of the tree on a device with no copy of it, until one of the entries stops listing it. A device that holds back a payload's note at a plain place, because the entry's signer may not take it, still seals that note back into the entry when it reseals, so a reseal by such a device vouches for the earlier signer. If a project is deleted on a device that has not yet seen a note move out of it, the deletion wins, as with plain folders, and since a deleted project's notes skip the trash, that note is gone. A note moved in by an editor whose entry a vault viewer signs again before another device sees it stays as a stale plain copy on that device, and that copy does not get the project's later edits. The protected folder itself (an entry's path, or a folder above one) cannot be renamed or moved, and neither can a note protected on its own by an older version ("Chronionego projektu nie można przemianować ani przenieść."): its envelope AAD, lead appointment, chat keys and the devices' baselines are bound to the path. Attachments keep the key they were uploaded under.
- A folder inside a protected folder can be protected on its own, with its own members and editors (nested entry). The parent's payload leaves out the nested folder's notes, folders and their history; the parent's members see the parent only as a bare container (`list_tree` lists its path among `folders`, not as a lock). Protecting a note is refused ("Notatki nie mają własnych uprawnień"); protecting a folder takes in the notes protected on their own by older versions: their keys are needed, and their entries go. Each payload is sealed without the notes of the entries nested under it, and resealed on the next save. Protect commands run one at a time per device, so two protects of one project cannot both seal a key.
- A protected folder is managed (`project_protect`, `project_set_members`) by its owner, admin, the project lead (for the folders of a project), or an editor of the protected folder above it while the folder has no protection of its own. The members dialog of anyone else is a read-only view; the bridge refuses the change in any case ("Uprawnienia może zmienić właściciel, administrator, prowadzący projektu lub edytor chronionego folderu nadrzędnego.").
- Top-level places (a new folder in the root or in `Projekty/`, a note in the root or in `Projekty/`, a new project) are the owner's and admins' (`create_note`, `create_folder`, `rename`, `rename_folder` refuse them for editors: "Główne foldery, notatki w głównym folderze i nowe projekty tworzy właściciel lub administrator."). An editor creates inside folders that are open or protected with the editor's write right. The tree listing sends `top: false` to an editor, which hides the root and "Nowy projekt" entries. Exception: a module's table note `Inwentarze/<name>.md`.

## Encrypted last name (contract)

The server no longer stores or returns a last name (nazwisko) in plaintext. Two encrypted copies replace it, both client-encrypted and opaque to the server.

- **Personal copy** `web_users.profile_secret`: the user's own profile, a `notes-key-v1` envelope encrypted with the personal key (the same key as `wrappedKey`). It is sent and read with `PATCH /api/auth/me` `{ profileSecret: <envelope> | null }`, returned as `profileSecret` by `/api/auth/me`, login and the account export. Its shape is checked by the `wrappedKey` validator (schema, nonce 12 B, ciphertext ≤ 4 KiB, and no `keyEpoch`).
- **Per-vault card** `vault_members.profile`: the member's last name as seen by one vault, a `notes-profile-v1` envelope under the vault key: `{ schema: "notes-profile-v1", keyEpoch: <int ≥ 1>, nonce: <12 B base64>, ciphertext: <base64, ≤ 1 KiB decoded> }`. Exactly these four keys are accepted. AES-GCM AAD = `notes-profile-v1\0<vaultId>\0<userId>\0<keyEpoch>`; the plaintext is JSON `{"lastName": "..."}`. Any member may write their own card (`PUT /api/vaults/:id/my-profile`, viewers included; 404 for non-members, 400 for a bad envelope). `GET /api/vaults/:id` returns `members[].profile` for every member (ciphertext, so all members may see it), or `null`. Cards are not rotated by key rotation: after a rotation the client re-encrypts its own card.
- **Legacy plaintext** `web_users.last_name` is only read so the client can migrate it: `/api/auth/me`, login and the export still return `lastName` (usually `""`). Registration and `PATCH /api/auth/me` reject any non-empty `lastName` with 400 ("Nazwisko jest teraz szyfrowane w przeglądarce…"); `lastName: ""` is accepted and clears the column. `members[].lastName` is removed from `GET /api/vaults/:id`.
- **Migration**: the client copies the legacy value into `profileSecret` and the vault cards, then clears it with `PATCH {lastName: ""}`, at the user's next login. The server does nothing on its own.

## Account preferences (contract)

Appearance and editor settings follow the account, so every device that signs in shows the same look.

- **Storage** `web_users.preferences` (TEXT, added by `ALTER TABLE` when missing): one `notes-key-v1` envelope encrypted with the personal key, the same shape and validator as `profileSecret` (ciphertext ≤ 4 KiB, so the plaintext is capped at about 3 KiB). Its content is one JSON object of the synced settings: `theme`, `accent`, `customAccent` (`#rrggbb`), `fontSize`, `editMode`, `lineNumbers`, `showToolbar`, `toolbarPosition`, `textWidth`, `spellcheck`, `writingLanguage`, `headingRail` (old copies may still carry `confirmDelete`, which is ignored), and the user's GitHub token as `githubToken` when one is saved (docs/GITHUB.md §7; not a setting: the settings screen and `applySyncedSettings` never see it, and it goes only to `api.github.com`). Device and per-space settings (`autoLoadImages`, `plugins`, `backupReminder`, `newNoteFolder`, window and layout state) never leave the device.
- **API**: `PATCH /api/auth/me` `{ preferences: <envelope> | null }` replaces or removes it (`null` removes; absent leaves it alone; a bad envelope → 400 "Nieprawidłowe zaszyfrowane dane profilu."). `preferences` is returned by `/api/auth/me`, login and the account export (`account.preferences`).
- **Client**: after sign-in (`syncPreferences` in `ui/src/preferences.ts`) the account copy is opened and applied over the local settings; an account without a copy gets this device's settings uploaded. A change to a synced setting is saved after a 1 s pause, as a whole object (last writer wins across devices). A copy that cannot be opened is left on the server and the local settings stay.
- Desktop (Tauri) has no account and keeps its settings local.

## Kosz (trash, contract)

- Deleting a note (or a folder's notes) moves it to the trash; it is not gone. Commands on every bridge: `list_trash` → `{ id, path, deleted_at }[]` (newest first), `restore_note { id }` → the restored path, `purge_note { id }` → removes one item for good.
- `state.folderFiles: [{ fileId, path, changedAt, deleted }]`: a server file placed in a folder of the tree
  (docs/PLIKI.md §7). Merged per `fileId`: the later `changedAt` wins, a removal wins a tie. Never inside a protected
  project (the client refuses the place; the snapshot is read by every member). Optional: older snapshots have none.
- `state.trash: [{ id, path, deletedAt, state }]`: the content of a deleted note, `state` a base64 Yjs update encoded like `yjsUpdateBase64`. Optional: older snapshots have none.
- Tombstones (`state.deleted`) gain two optional clocks: `restoredAt` (a restore) and `purgedAt` (an emptied item, kept without content). A note is deleted while its `deletedAt` is later than its `restoredAt`, so a later restore beats an older delete, and a newer delete beats an older restore. Each clock merges by the later value.
- A trash item is kept only while it matches the latest delete of its note (`deletedAt` equal) and is not purged. Two copies of the same delete merge their Yjs states. A purged item is not brought back by an older copy, because its tombstone keeps `purgedAt`.
- The trash is purged after `TRASH_DAYS` = 183 days from the delete, on export and on merge, together with the note's versions.
- Protected projects: a trashed note inside a protected folder is in the entry's sealed payload (`trash` in the payload, its id in `noteIds`), never in the plain `state.trash`. Only a key holder lists it, restores it or purges it.
- Deleting a whole protected project (`delete_folder` with deleted marks) stays permanent: its notes do not go to the trash, and the mark drops their trash items too. The dialog says so ("Chroniony projekt zostanie usunięty na zawsze.").

## Claude chats (MCP, contract for docs/MCP.md version 1)

Design and rules: docs/MCP.md. This section is the wire contract all parts follow (server `crates/node/src/agents.rs`,
browser `ui/src/agentcrypto.ts`, `ui/src/proposals.ts`, `ui/src/agents.ts`, MCP `mcp/`). Version 1: no compartments
(every vault in a chat's scope is `whole: true`, `parts: []`); folders are narrowed softly by the sealed scope.

### Encodings and primitives

- `b64u`: base64url without padding. `hex`: lowercase. Text is UTF-8. `\n` below is one LF byte.
- Chat keys: Ed25519 signing pair (libsodium `crypto_sign_keypair`), X25519 box pair (`crypto_box_keypair`). Public keys
  travel as `b64u` of their 32 bytes (`signKey`, `boxKey`). Server side: `ed25519-dalek` (verify only), `blake2`.
- `H(x)`: BLAKE2b-256 (libsodium `crypto_generichash(32, x)`; Rust `blake2::Blake2b<U32>`).
- Pairing code: 8 symbols of `ABCDEFGHJKMNPQRSTUVWXYZ23456789`, shown `XXXX-XXXX`. Normalized: uppercase, `-` and spaces
  removed. The server stores `sha256 hex` of the normalized code only.
- Claim proof: Ed25519 detached signature (`b64u`) over `"notes agent-claim v1\n" + code + "\n" + signKey + "\n" + boxKey`.
- Check code (6 digits, shown by the browser and by the MCP): `H("notes agent-pair v1\n" + signKey + "\n" + boxKey + "\n" + code)`,
  first 4 bytes as big-endian uint32, `mod 1000000`, zero-padded to 6.
- Sealed to a chat (`notes-agent-sealed-v1`): `{ schema: "notes-agent-sealed-v1", box: b64u(crypto_box_seal(context + key, chatBoxKey)) }`
  where `context` = `"notes-agent-sealed-v1\n" + vaultId + "\n" + slot + "\n" + keyEpoch + "\n"` and `key` the 32 raw key bytes.
  `slot` is `vault` for a vault key and `project:<path>` for a protected project's key. The chat opens it and refuses a box
  whose context is not exactly the one it asked for (another vault, slot or epoch).
- Signed by a user: the existing ECDSA P-256 `signEvent` / `verifySigned` (signing.ts): `signerUserId`, `signature` over the
  canonical JSON without `signature`.
- Signed by a chat: Ed25519 detached signature over the same canonical bytes (canonical JSON without `signature`), with
  `signerUserId` = the chat's person, `signerAgentId`, `alg: "ed25519"`, `signature` = `b64u`.

### Certificate (`notes-agent-cert-v1`) and scope (`notes-agent-scope-v1`)

- `cert = { schema: "notes-agent-cert-v1", agentId, userId, signKey, boxKey, vaults: [{ vaultId, whole: true, parts: [], writeMode, fileText? }], createdAt, expiresAt }`
  signed by the person (`signerUserId` = `userId`). `agentId`: 32 hex, made by the browser. `fileText` (optional
  boolean, docs/OCR.md §5.2): "Tekst z plików"; left out = off, so certs from before it stay valid. `writeMode`:
  `none | proposals | append | direct`. `expiresAt` ≤ `createdAt` + 90 days. `vaults` is never empty.
- A chat's signature is valid when: the cert verifies under `userId`'s signing key, the event's `signerAgentId` is the
  cert's `agentId`, the Ed25519 signature verifies under `cert.signKey`, the cert is not revoked (`revokedAt`, from the
  server) at the event's time, and the event's time is before `cert.expiresAt`.
- `scope = { schema: "notes-agent-scope-v1", agentId, vaultId, include: [path], exclude: [path], tools: [name], tasks: "mine" | "all", updatedAt }`
  signed by the person, then sealed: `sealedScope = { schema: "notes-agent-sealed-scope-v1", box: b64u(crypto_box_seal(utf8(JSON(scope)), chatBoxKey)) }`.
  `include` empty = everything the chat can decrypt; `exclude` wins; a path covers itself and everything under it. `tools`
  empty = the default tools of docs/MCP.md §7 (`move_note`, `trash_note` off); not empty = exactly the tools allowed (`scope_info` always), so the app writes the defaults plus the extra ones picked. In MCP answers a note the chat may not see and a note that does not exist look the same ("Poza zakresem tego czatu."); a link to a note the chat may not see is shown as an opaque mark `⟦ukryty link n⟧`, put back as the original link when the chat writes the note (a missing, changed or new mark refuses the write). The MCP refuses a scope whose signature fails
  or whose `updatedAt` is older than the newest it saw for that vault, and then shows nothing of that vault.

### Request proof (every chat request but the claim)

Headers: `Authorization: NotesAgent <sessionToken>` (64 hex; absent on `GET /api/agent-pair/:token`), `Notes-Agent-Time`
(unix ms), `Notes-Agent-Nonce` (32 hex), `Notes-Agent-Version` (semver), `Notes-Agent-Proof` = `b64u` Ed25519 signature over
`"notes-agent-req-v1\n" + METHOD + "\n" + pathAndQuery + "\n" + hex(H(body)) + "\n" + time + "\n" + nonce + "\n" + version`
(empty body: `H` of zero bytes). The server checks: version present (400), version ≥ `NOTES_AGENT_MIN_VERSION` (426), chats
on (503), the signature under the chat's `signKey`, time within ±60 s, nonce unseen for 5 minutes. A chat token is never a
cookie, so no other `/api/*` route accepts it.

Errors to chats are JSON `{ code, message }`: `session` (401: unknown, expired or idle token), `paused` (403: new IP or
limits, until the person confirms), `scope` (404: vault not in scope, same as for a non-member), `read-only` (403),
`limit` (429), `version` (426), `disabled` (503), `proof` (401), `conflict` (409, with `revision`, `envelope`),
`stale-key` (409).

### Authors of revisions

The sync frames `snapshot`, `ack`, `update` and `conflict` carry `author: { userId, agentId } | null`, set by the server from
the session that wrote the stored revision (`null` for revisions stored before this field). A client never sends an author.

### Protected projects

An entry may carry `agentKeys: [{ agentId, userId, sealedKey }]` (slot `project:<path>`), signed with the entry. Each
`userId` must be in `members`, and a change of the `agentKeys` of a person must be signed by that person or by a manager
(removing them); anything else flags the entry. Rotating a project key seals it for the remaining `agentKeys`. A device that holds a project's key and may manage it (or is the chat's person) drops the `agentKeys` of chats revoked since (`members[].agents[].revokedAt`), or all of them when the policy does not allow protected projects, with a new project key. Version 1: an entry signed by a chat is never trusted (a chat writes into a protected project only through a proposal).

### Undoing a chat's changes (docs/MCP.md §7.2)

Before merging a revision written by a chat, a member's app keeps a version of each note it changes with the reason
`Przed zmianą Claude (<agentId>)`, and after it one with `Po zmianie Claude (<agentId>)`. "Cofnij zmiany czatu" puts a
note back to the version before the chat's first change in the window only when nobody changed it since the chat did;
otherwise it cuts out just the chat's text when that text occurs exactly once, and else leaves the note as it is and
lists it as a conflict to settle. A note done so gets `Cofnięto zmiany Claude (<agentId>)`, so undoing again changes
nothing. A note the chat created goes to the trash. Both versions carry the note's `path` then. A note the chat moved goes back to its path from before, when nobody moved it since and the path is free (else a conflict). In every write mode a chat's revision may add task events only to the organization data: any
other change of it (members, groups, aliases, fields: groups decide access through `grupy:`) refuses the revision, as do any changes of a
chat in `none` or `proposals`. A refusal is decided on the newest members and certs (fetched again first).

### Proposals (`notes-proposal-v1`)

`{ schema: "notes-proposal-v1", proposalId (32 hex), agentId, epk (JWK P-256), nonce (b64), ciphertext (b64), signerUserId, signerAgentId, alg: "ed25519", signature }`.
Key: HKDF-SHA256(ECDH(ephemeral P-256, person's box key), salt 32 zero bytes, info `"notes-proposal-v1\0" + vaultId + "\0" + proposalId`)
→ AES-GCM-256, AAD `"notes-proposal-v1\0" + vaultId + "\0" + proposalId + "\0" + agentId`. Plaintext: gzip of JSON
`{ createdAt, summary, changes: [{ op: "create" | "append" | "edit" | "move" | "trash" | "tasks", path, noteId, baseHash, text?, to? }] }`;
`baseHash` = `hex(H(utf8(current text)))`, empty string for `create`. `text`: for `append` and `tasks` the text added at the end, for `edit` and `create` the whole new text; `move` has the new path in `to`; moving or trashing a note with permission marks is refused like changing them. The person's app shows it, checks the signature, the
AAD fields and `baseHash`, refuses changes to `osoby:`, `grupy:`, `prowadzacy:` and `!zaznacza:`, and applies an approved one
with the person's own client.

## Leases (GitHub, contract)

Short, opaque locks on a shared vault, so that one device at a time updates a GitHub project (docs/GITHUB.md §5). The server does not know what a lease guards.

- `POST /api/vaults/:id/leases` with `{ "name": "<32 lowercase hex>", "ttlSeconds": 1..300 }` → `200 { "granted": true, "until": <ms> }` for a new lease, an extension by the holder, or a takeover after expiry; `200 { "granted": false, "until": <ms> }` while someone else holds it (`until` is the holder's end).
- `DELETE /api/vaults/:id/leases/:name` → `204`. Only the holder releases its lease; a missing or someone else's lease is a no-op with the same `204`, so nothing is revealed.
- Holder = user and device session (a hash of the session token). The same user on another device is refused like anyone else.
- Roles: owner, admin and editor may take leases; viewer → `403`; not a member or unknown vault → `404`. Personal vaults (`browser-<userId>`) → `400`.
- A lease lasts `ttlSeconds` from the request; expired rows are deleted on every POST for that vault. At most 50 active leases per vault; the 51st → `429`.
- Errors carry `{ "error": "<message>" }`. A malformed name or ttl → `400`.
- Names and holders are never logged or written to the audit log.
- Stored in `vault_leases(vault_id, name, holder, until)` in `auth.db`; rows go with their vault (`ON DELETE CASCADE`).
